# Graph Document Generation Procedure

This prompt defines how to **generate** a Graph Document (GD) that serves a stated goal — a question, a problem, a task, a consultation — by combining content from a GD database, the AI's own knowledge, and a human's input, iteratively.

It assumes the companion document **"GDdef"** (node/link structure, relation types, and the relation selection rule) is provided together with this prompt.

---

## 1. Node and link origin

Every node and every link must carry an **origin** tag and a **status**:

- `origin`: one of
  - `db` — retrieved from the GD database (an existing, previously stored node/link)
  - `ai` — generated by the AI during this session (reasoning, synthesis, a proposed solution, a proposed connection)
  - `human` — authored, edited, or explicitly approved by the human
- `status`: one of
  - `proposed` — an `ai`-origin node/link not yet reviewed by the human
  - `confirmed` — approved by the human, or originally `db`/`human` origin

A `db`-origin node must also carry a `source_id` pointing back to its record in the GD database, so its provenance remains traceable after it is copied into the working GD.

An `ai`-origin node becomes `human`-origin only when the human explicitly edits its text; it remains `ai`-origin (with `status: confirmed`) when the human merely approves it unchanged. This distinction matters for later trust/quality assessment of the database.

---

## 2. Rules for AI-generated content

- An `ai`-origin node must be clearly framed as either (a) a synthesis or restatement of retrievable, verifiable knowledge, or (b) an explicit proposal/suggestion (a candidate solution, a candidate connection, a candidate next question) — never presented with unwarranted certainty as established fact.
- Do not present an `ai`-origin node as if it were `db`-origin. If a node's content resembles guidance from an authoritative source (e.g., a guideline database) but was actually composed by the AI from general knowledge rather than retrieved from the DB, it must be tagged `ai`, not `db`.
- When the goal domain carries real-world stakes (health, legal, financial, safety), any `ai`-origin node offering a course of action must remain `status: proposed` until a human confirms it — never auto-promote to `confirmed`.
- The AI may propose deleting or revising an existing `db`-origin or `human`-origin node (e.g., flagging it as outdated or inapplicable to this case), but must not silently delete it — deletion of non-`proposed` content requires human confirmation.

---

## 3. The generation loop

Repeat the following loop until the sufficiency check in Section 4 passes:

1. **Interpret the goal**: Identify what question, problem, or task the resulting GD must serve. Keep this goal statement itself as a node (typically `human`-origin) so it stays visible as the GD grows.
2. **Search**: Query the GD database for existing nodes/links relevant to the current state of the GD (the goal, and any nodes added so far). Import matches as `db`-origin, `status: confirmed` nodes, linked in via the relation type that precisely applies.
3. **Propose**: Where the database has no directly relevant content, or where a gap remains between what is known and what the goal requires, generate candidate `ai`-origin nodes/links (`status: proposed`) — a missing causal link, a candidate solution, a clarifying question to put to the human, a relevant distinction.
4. **Elicit human input**: Present new candidates to the human. For each:
   - **Approve** → `status: confirmed`, `origin` unchanged.
   - **Edit** → `status: confirmed`, `origin: human`.
   - **Reject/delete** → remove the node/link entirely (do not keep a "rejected" node in the working GD; if it is useful to remember what was tried and discarded, that fact itself becomes a `human`-origin node, e.g., "X was tried and did not help").
   - **Ask for more** → return to step 2 with a refined query informed by the human's answer.
5. **Re-check goal fit**: After each round, compare the current GD against the goal statement from step 1. If it does not yet answer/address the goal, continue the loop; if it does, proceed to Section 4.

---

## 4. Sufficiency check ("just enough")

A generated GD is complete when it satisfies **all** of the following, and incomplete otherwise:

- **Covers the goal**: Every part of the stated goal (Section 3, step 1) is addressed by at least one node/link in the GD.
- **No dangling gaps**: No node exists that raises a question or a problem without either a resolving node or an explicit acknowledgment that it remains open.
- **No redundant surplus**: No node duplicates the informational content of another node already in the GD; no `ai`-origin proposal remains in `status: proposed` after being rejected (see Section 3, step 4) or superseded by a better one.
- **No dead ends from rejected content**: Content the human indicated is ineffective, inapplicable, or wrong must be removed, not merely left uncorrected alongside its replacement.
- **Domain-required safety/authority nodes are present, not just implied**: If the goal domain has a known threshold at which the GD's own content is insufficient and an external authority should be consulted (a professional, a specialist database, a regulator), that threshold must be present as an explicit node/link — it must not be left as something the human is assumed to already know.
- **Every node's origin and status is set**: No node/link is missing its `origin`/`status` tags.

If any of these fail, return to the loop in Section 3 rather than emitting the GD.

---

## 5. Output schema

Emit the result as a single JSON object:

```json
{
  "goal": "text of the goal statement node",
  "nodes": [
    { "id": "n1", "text": "...", "origin": "human", "status": "confirmed" },
    { "id": "n2", "text": "...", "origin": "db", "status": "confirmed", "source_id": "db://guideline-corpus/12345" },
    { "id": "n3", "text": "...", "origin": "ai", "status": "proposed" }
  ],
  "links": [
    { "relation": "Causes", "source": "n2", "target": "n1", "origin": "ai", "status": "confirmed" },
    { "relation": "Contrast", "sourceNodes": ["n1", "n3"], "origin": "human", "status": "confirmed" }
  ]
}
```

Structural rules for `links` are unchanged from the companion documents: an asymmetric relation uses `source`/`target`; a symmetric relation uses `sourceNodes` (two or more ids, no `target`). Every link additionally carries its own `origin`/`status`, since a link (a claimed relationship) can be proposed and confirmed independently of the two nodes it connects.

Do not emit a GD that still contains any `status: proposed` node/link unless the interaction is explicitly paused for human review at this point (i.e., this is an intermediate, not final, output).
